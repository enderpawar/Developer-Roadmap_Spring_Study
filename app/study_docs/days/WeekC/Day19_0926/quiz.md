## 2. 예측과 실행 — N+1 (`findAllTriggersNPlusOneSelects`)

| # | 질문 | 학습자 1차 예측 | 판정 |
|---|---|---|---|
| P1 | `findAll()` 구간 member select 횟수 | "3" | ❌ |
| P2 | 순회 구간 member select 횟수 | "4" | ❌ |
| P3 | 총 select 횟수 | "7" | ❌ |

힌트(LAZY가 미루는 게 정확히 뭔지) 제공 후에도 "잘 모르겠다"는 답변이 나와, 메커니즘을 직접 설명한 뒤 실행으로 확인하는 방식으로 진행했다. 실행 결과: `findAll()` 구간 0번(FK값만 딸려오고 member는 아직 프록시 상태) → 순회 구간 3번(진우·철수·영희 각 1번, `getMember().getName()` 호출마다) → 총 4번.

## 4. 설계 판단 — 인터페이스 확장 시 default 메서드 몸통

`ReservationRepository`에 `findAllWithMember()`를 추상 메서드로 추가했다가 대조군 구현체(`InMemoryReservationRepository`, `JdbcReservationRepository`) 컴파일이 깨져서, `default` 메서드로 전환. 몸통을 옵션 A(`return findAll();`로 폴백) vs 옵션 B(`throw`로 즉시 실패) 중 **B**로 선택.

- 1차 근거: "실제로 호출되지 않는 대조군 코드라 결과를 동작시킬 필요가 없다" — 판단 근거가 "현재 상태"에만 머물러 있었음
- 교정 후 근거: "나중에 실수로 이 구현체가 다시 연결되면, A는 조용히 최적화 없는 결과를 내서 아무도 눈치 못 채지만 B는 즉시 실패해서 바로 드러난다"는 fail-fast 근거까지 스스로 연결

## 5. 복습 일정

self-invocation은 여전히 미통과라 **+1(9/27) 재시험**. `transactionalOuter`·Entity 기본 생성자 항목은 통과해 **+2(9/28)로 복귀**. 오늘 신규 등록한 N+1·fetch join·인터페이스 확장 전파 개념은 **+2(9/28)** 인출 예정. 상세는 `복습큐.md` 참고.
