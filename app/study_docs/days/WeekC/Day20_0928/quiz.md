# Day20 (9/28, Week C D6) 누적시험 A+B+C 기록

범위: Week A(웹 계층) 전체 + Week B(Flyway·JDBC·JPA·영속성 컨텍스트·변경 감지) + Week C D1~D5(트랜잭션 경계·AOP 프록시·전파·LAZY 프록시·N+1)

| # | 질문 | 학습자 답 | 판정 | 교정 |
|---|---|---|---|---|
| 1 | DTO(record)와 Domain을 왜 분리하나 | "Domain은 상태 변경이 필요해서 record로 못 만드니까 가변으로 두고, DTO는 경계를 넘기만 하니까 record로 불변화" | ✅ | Day13에서 교정한 인과 순서(역할→성질) 그대로 재현, 힌트 불필요 |
| 2 | 생성자 주입을 쓰는 이유 | "구현 교체해도 Service 코드 안 바뀌고, 테스트에서 다른 구현으로 바로 교체 가능" | ✅ | 두 가지 핵심 이유를 힌트 없이 바로 답함 |
| 3 | 순수 JDBC 대비 JPA가 실제로 추상화하는 것 | "커넥션 풀은 그대로 쓰고, Hibernate가 매핑이랑 SQL 생성을 대신 해주는 것" | ✅ | "커넥션 풀을 없앤다"는 오답 함정을 스스로 피함 |
| 4 | 같은 트랜잭션에서 같은 id를 두 번 조회하면 SELECT는 몇 번이고 두 결과는 같은 객체인가 | "1차 캐시에 걸려서 SELECT 1번, 같은 참조" | ✅ | 정확 |
| 5 | `save()` 없이 `UPDATE`가 나가는 원리(dirty checking)와 Flyway 체크섬의 차이 | "dirty checking은 필드값을 로드 스냅샷이랑 비교해서 flush 때 UPDATE 만드는 거고, Flyway 체크섬은 마이그레이션 파일 해시를 기동 시점에 비교하는 거라 둘은 다른 장치" | ✅ | Day13에서 혼동했던 두 개념을 이번엔 힌트 없이 구분 |
| 6 | `@Transactional`이 애노테이션만으로 어떻게 동작하는가(self-invocation 포함) | "프록시가 메서드 호출을 가로채서 트랜잭션을 시작·종료하는 거고, target 안에서 `this.inner()`로 부르면 프록시를 다시 안 거쳐서 적용이 안 됨" → (근거를 묻자) "그냥 프록시가 아니니까 적용이 안 되는 거 아니에요?" | ❌ | 결론(적용 안 됨)은 맞지만 근거가 다시 순환논리로 돌아감. "`this`는 바이트코드 수준에서 `invokevirtual`로 대상 객체 자기 자신을 직접 가리키고, 그 대상은 애초에 프록시로 재대입된 적이 없다"는 설명을 다시 듣고서야 "프록시가 아예 그 호출 경로에 없다"고 재구성함. 세 번째 통과이지만 매번 근거가 무너져 **오답으로 기록**하고 복습큐에 다시 올림 |
| 7 | 트랜잭션 전파 `REQUIRED`와 `REQUIRES_NEW`의 판단 로직 대비 | "REQUIRED는 있으면 합류, 없으면 새로 시작. REQUIRES_NEW는 있어도 무시하고 항상 새로 시작(기존 건 잠깐 보류)" | ✅ | Day17에서 교정한 표현 그대로 재현 |
| 8 | `REQUIRES_NEW` 실행 중 위험한 이유 | "위험하다고는 배웠는데... 트랜잭션이 두 개라서?" | ⚠️ 힌트 후 통과 | "두 트랜잭션이 **동시에 열려 있는 동안 무엇을 두 개 쓰는가**"라는 힌트 후 "커넥션을 2개 동시에 물고 있어서 풀이 꽉 차면 병목·대기가 생긴다"까지 도달 |
| 9 | Spring AOP 프록시와 Hibernate LAZY 프록시가 같은 장치인가 | "둘 다 프록시니까 결국 같은 원리 아니에요? 어차피 뭔가를 가로채는 거잖아요" | ❌ | "가로챈다"는 공통점만 보고 가로채는 **대상**(메서드 호출 vs 필드 접근)과 **목적**(부가기능 삽입 vs SELECT 지연)이 다르다는 걸 놓침. `ReservationService$$SpringCGLIB$$0`(Day16)과 `Member$HibernateProxy`(Day18)를 나란히 놓고 "이름에 SpringCGLIB가 들어간 것과 HibernateProxy가 들어간 것 중 어느 쪽이 SQL을 지연시키느냐"는 질문을 받은 뒤에야 구분해서 재답변 |
| 10 | N+1과 fetch join — fetch join을 한 번 쓰면 매핑 자체가 바뀌는가 | "fetch join으로 확인했으니까 이제 `findAll()`도 자동으로 JOIN으로 나가는 거 아니에요?" | ❌ | fetch join은 **그 쿼리 메서드 하나에만** 적용되는 쿼리 수준 힌트이고, `Reservation.member`의 매핑(`FetchType.LAZY`)은 그대로다. `findAll()`은 여전히 N+1을 낸다는 것을 `NPlusOneTest`가 두 메서드를 별도로 검증한다는 사실로 재확인 |

## 총평

10문항 중 힌트 없이 통과 6개, 힌트 후 통과 1개, 오답 2개(6번·9번). Week A·B는 이미 여러 차례 재시험을 거쳐 안정됐고, 이번에 흔들린 건 전부 Week C였다 — 로드맵이 이 주를 "벽"으로 지정한 것과 일치한다. 6번(self-invocation)은 세 번째 도전인데도 근거가 매번 다른 방식으로 무너져, 이번엔 통과가 아니라 오답으로 기록해 복습큐에 남긴다. 9번은 "프록시"라는 한 단어가 서로 다른 두 장치(Day16의 AOP 프록시, Day18의 Hibernate 프록시)를 가리는 전형적인 사례였다.
