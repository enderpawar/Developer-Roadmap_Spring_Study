# Day28 (10/10, Week D D7 버퍼) 인출 기록

새 개념 인출보다, Day27 시험 7번 문항(401·403을 만드는 주체 구분)에서 교정한 기준을 실제 코드 부채 상환에 쓰는 데 집중한 날이다.

## 1. 설계 판단 — 401/403 응답 통일 범위

| # | 질문 | 학습자 판단 | 근거 | 판정 |
|---|---:|---|---|---|
| P1 | `GlobalExceptionHandler`의 401과 `CustomAuthenticationEntryPoint`의 401을 하나로 합쳐야 하는가 | 아니오, 각자 위치는 유지하고 응답 **모양**만 통일한다 | Day27에서 교정한 대로 둘은 서로 다른 주체(MVC 예외 처리 vs 필터 단계)가 만드는 게 맞다. 주체를 합치는 게 아니라 결과물의 필드 구성을 맞추는 문제다 | ✅ |
| P2 | 기존 `error` 필드를 지우고 새 형식으로 바꿔야 하는가 | 아니오, `error`는 유지하고 `code`·`timestamp`만 추가한다 | 필드를 지우면 기존 `jsonPath("$.error")` 단언이 전부 깨진다 — 굳이 깨질 필요가 없는 변경이다 | ✅ |
| P3 | `CustomAuthenticationEntryPoint`도 `GlobalExceptionHandler`처럼 `Map`을 Jackson으로 직렬화하도록 바꿔야 하는가 | 아니오, 이번엔 기존 문자열 조합 방식 그대로 두고 필드만 추가한다 | 리팩터링까지 하면 이번 부채 항목("401/403 일관성")의 범위를 벗어난다. 문자열 이스케이핑 위험은 남지만 메시지에 특수문자가 없어 당장은 낮다고 판단 | ✅ |

## 2. 판단 로직 — 범위를 넓히지 않는 것도 판단이다

400(Validation)·404(NotFound)·409(Duplicate)·500(Unexpected) 응답에도 `code`·`timestamp`를 넣을지 검토했다. 넣지 않기로 했다 — 이번 부채 항목은 기술부채 원장에 "401/403 일관성"으로 범위가 명시돼 있었고, 나머지 상태 코드까지 넓히면 이 버퍼 세션 하나로 끝내기 어려운 별도 작업이 된다.
